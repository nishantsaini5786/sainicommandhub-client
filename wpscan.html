WPScan is a WordPress security scanner designed for security professionals and site maintainers to test WordPress installations. It can identify WordPress versions, themes, plugins and other interesting findings, while its vulnerability intelligence can be enhanced with a WPScan API token.

What is WPScan? (Deep Theory)

WPScan is a black-box WordPress security assessment tool. Its core workflow is discovery first, followed by targeted enumeration and then vulnerability correlation. The scanner is not a substitute for manual validation: a detected component or version should be checked against the actual installation and the relevant advisory before a finding is treated as confirmed.

Core Concepts

  • Target: the authorized WordPress URL being assessed.
  • Fingerprinting: identifying WordPress and clues about its version, themes and plugins.
  • Enumeration: using -e to discover users, plugins, themes, backup artifacts and other supported objects.
  • Plugin detection: passive, mixed or aggressive approaches trade request volume against discovery depth.
  • Vulnerability intelligence: WPScan can query its vulnerability database when an API token is available.
  • Evidence: preserve the scanner version, target, timestamp, configuration and output so results are reproducible.

Mental Model

TARGET → FINGERPRINT → ENUMERATE → CORRELATE → VALIDATE → REPORT

💡
Important: WPScan is meant for authorized WordPress security testing. Use a local VM, your own site, a CTF or another target where you have explicit permission.
Installation & First Checks

Kali

Verify installation

wpscan --version

Check help

WPScan is commonly available on Kali. The current upstream project also documents Docker as an installation/runtime option. Keep the local database current before a lab assessment when vulnerability intelligence matters.

Plugin Detection Strategy

WPScan documents passive, mixed and aggressive plugin-detection modes. Passive detection is useful when keeping request volume low; mixed detection can improve discovery; aggressive detection may create more requests and should be reserved for controlled assessments.

ModeConceptUse in a lab
passiveInfer plugins from available page/content cluesBaseline / low-noise inventory
mixedCombine passive clues with additional checksBalanced enumeration
aggressiveMore active plugin discoveryDedicated test environments
API & Vulnerability Intelligence

WPScan can use its WordPress vulnerability database API for vulnerability information associated with detected WordPress, plugins and themes. The API token can be supplied with --api-token, through the WPSCAN_API_TOKEN environment variable, or via a configuration file. Current upstream documentation states that free accounts receive up to 25 API requests per day; after that, WPScan continues to work but without vulnerability data.

🔑
Never commit an API token to GitHub or place it in screenshots. Prefer an environment variable or protected local configuration.
Configuration Files

WPScan can load CLI options from JSON or YAML configuration files. Current upstream documentation lists XDG configuration locations such as ~/.config/wpscan/scan.yml and legacy ~/.wpscan/scan.yml.

Recommended lab sequence

  1. Record wpscan --version and update the local database.
  2. Run a baseline scan against your WordPress VM.
  3. Enumerate vulnerable plugins and themes.
  4. Use mixed detection when deeper plugin discovery is appropriate.
  5. Supply an API token only when you need vulnerability intelligence.
  6. Review every finding manually and record evidence.
  7. Export/log the final result and document remediation.

Troubleshooting

“Does not seem to be running WordPress”

Confirm the URL, redirects, reverse-proxy behavior and whether the target actually exposes WordPress. Use --force only when you have a reason to override detection.

Too many requests

Reduce concurrency with --max-threads, add --throttle, and choose a narrower enumeration set. Do not treat a production site like a CTF target.

No vulnerability data

Check your API token, daily API request allowance, network connectivity and the WPScan API service status. A scanner can still enumerate components without current vulnerability intelligence.

Plugin not detected

Try a suitable plugin detection mode, confirm the custom wp-content/plugins paths, and manually validate the site source. Discovery is not guaranteed.

Certificate errors in a lab

Prefer fixing the lab certificate. --disable-tls-checks exists for controlled scenarios where certificate validation intentionally cannot be performed.

Responsible Use

Only scan WordPress installations you own or are explicitly authorized to assess. Enumeration can generate significant HTTP traffic and may expose usernames or backup artifacts. Keep API tokens private, minimize request volume, preserve evidence securely, and report findings with enough context for remediation.
