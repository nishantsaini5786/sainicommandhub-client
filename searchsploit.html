SearchSploit is the command-line search utility bundled with Exploit-DB. It searches a local copy of Exploit-DB, making it useful when researching software names, versions, CVEs and vulnerability classes from a Kali terminal—even on segregated or offline assessment networks.

What is SearchSploit? (Deep Theory)

SearchSploit is best understood as a local exploit-reference search engine, not as an exploitation framework. It helps you discover public exploit and proof-of-concept references that may relate to software you have identified during an authorized assessment.

Where it fits in a pentest

  1. Recon: identify the host, service, product and version.
  2. Fingerprinting: confirm the product/version with reliable evidence rather than trusting one banner.
  3. Research: search SearchSploit using product, version, vulnerability class or CVE.
  4. Validation: compare the candidate entry with vendor advisories, affected-version ranges and your actual target.
  5. Controlled testing: only test an exploit in an explicitly authorized environment and within scope.
💡
Important: A SearchSploit result is not proof that a target is vulnerable. Public exploit entries can be incomplete, version-specific, unreliable, or unrelated to your exact build. Treat them as research leads that require verification.

SearchSploit vs Exploit-DB website

SearchSploit works primarily against a local repository/index. The online Exploit-DB site can provide additional metadata and context that is not represented in the local search output. The -w option can help you locate the online entry.

Understanding Search Matching

AND matching

SearchSploit generally uses multiple supplied terms together to narrow results rather than treating them as an OR query. Adding more terms can therefore reduce the result set.

Broad first, precise second

If a highly specific query returns nothing, start with a broader product/version family and then narrow using -t, -e, -s, exclusions or a CVE.

Why paths can create false positives

Default searching can consider both exploit titles and file paths. A numeric version or platform name may therefore appear in a path even when it is not the actual affected product/version. Title-only searching can reduce that noise.

Search terminology matters

Use descriptive security terms instead of relying on abbreviations. For example, searching for SQL Injection can be more useful than only searching for SQLi.

Nmap → SearchSploit Workflow

A common authorized workflow is to first collect service/version information with Nmap and then correlate those versions against the local Exploit-DB index.

nmap -sV -oX scan.xml TARGET searchsploit --nmap scan.xml
  1. Scan only the authorized target.
  2. Review the service/version output manually.
  3. Feed the XML file to SearchSploit.
  4. Investigate candidate EDB-IDs.
  5. Verify the exact affected version/build.
  6. Check the original advisory and exploit source before any controlled validation.
EDB-ID → Source Review Workflow
searchsploit -p EDB-ID searchsploit -x EDB-ID searchsploit -w EDB-ID

-p helps locate the local file, -x opens the entry for examination, and -w exposes the online Exploit-DB reference. The review step should focus on affected versions, prerequisites, platform, exploit type, reliability and whether the entry actually matches your target.

Common Troubleshooting

“searchsploit: command not found”

Install the Kali package and verify that the executable is in PATH.

sudo apt update sudo apt install -y exploitdb command -v searchsploit

Results look unrelated

Try title-only searching, exact matching, a broader version family, or exclusions. Numeric terms can match file paths and produce noise.

No results for a known product

Try the vendor/product name separately, remove an over-specific version, and then narrow the results. Also verify whether the local Exploit-DB data is current.

Nmap correlation does not work

Make sure the XML file exists and was created with service/version information. SearchSploit's Nmap mode expects Nmap XML input.

Database appears stale

searchsploit -u
Practical Lab Exercise

Goal: practice the full research workflow without attacking a real-world system.

  1. Start a vulnerable VM such as a deliberately vulnerable training machine.
  2. Identify its services and versions with Nmap.
  3. Export service/version results to XML.
  4. Run searchsploit --nmap against that XML.
  5. Pick one candidate EDB-ID and inspect it with -p and -x.
  6. Use -w to compare the local result with its online Exploit-DB entry.
  7. Document why the entry does or does not match the exact software build.
🧠
Learning objective: The important skill is not memorizing exploit IDs. It is connecting service → exact version → vulnerability → public reference → validation decision.
Important Concepts to Remember
  • EDB-ID: Exploit-DB's identifier for an entry.
  • CVE: A standardized vulnerability identifier; an EDB entry and a CVE are not the same thing.
  • PoC: Proof-of-concept code or demonstration; availability does not guarantee reliability or applicability.
  • Local index: The data SearchSploit searches locally.
  • Nmap XML: Structured service/version output that SearchSploit can correlate.
  • Mirror: Copy an exploit entry to the current working directory for local review.
  • Examine: Open an entry using the configured pager.
