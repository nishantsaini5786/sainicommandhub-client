sqlmap is an open-source penetration-testing tool designed to automate detection and exploitation of SQL injection flaws and database-server takeover paths. For SAINICOMMANDHUB, the examples below are framed around intentionally vulnerable applications, local VMs and authorized security assessments. The official usage guide covers URL/request-file targets, request customization, detection levels and risk, SQLi techniques, database enumeration, custom SQL, sessions, reporting and the REST API.

What is SQLMap? (Deep Theory)

SQL injection happens when application input changes the structure of a database query. A vulnerable application might concatenate an untrusted value into SQL instead of safely parameterizing it. SQLMap automates much of the repetitive work: it compares responses, tests different SQL injection techniques, fingerprints the DBMS, and—when the authorized target permits it—enumerates databases, tables and columns.

DETECTION

SQLMap can test parameters using Boolean-based, error-based, UNION-based, stacked-query, time-based and inline-query techniques.

FINGERPRINTING

After identifying injection behavior, SQLMap can fingerprint the backend DBMS and retrieve version/banner information.

ENUMERATION

Authorized lab testing can progress from databases → tables → columns → selected records.

AUTOMATION

Request files, batch mode, saved sessions, traffic logs, JSON reports and API integration make repeatable testing possible.

Important: detection is not the same as proof of impact

A successful SQL injection finding should be validated carefully. A banner, database name or table list is evidence of database access, but the security impact depends on application privileges, exposed data and the surrounding system design.

SQL Injection Techniques
CodeTechniqueConcept
BBoolean-based blindInfer results from differences between true/false responses.
EError-basedUse database error behavior to obtain information.
UUNION query-basedCombine attacker-controlled SELECT output with the original query.
SStacked queriesAttempt additional statements where the DBMS/application supports them.
TTime-based blindInfer a condition from controlled response delays.
QInline queriesUse inline SQL expressions supported by the backend.

SQLMap's documented default technique set is BEUSTQ. The exact technique that works depends on the application, DBMS and query context.

Level vs Risk

LEVEL 1

Default detection depth. Good starting point for a lab target.

LEVEL 3

Broader testing, including additional request locations such as cookies depending on the level.

LEVEL 5

Much broader payload/boundary testing and substantially more requests.

RISK

Controls how potentially heavier or more dangerous tests are considered. Higher risk should be reserved for controlled environments.

The official sqlmap guide documents five detection levels and three risk levels. Start low, then increase only when the assessment scope and target stability allow it.

Request Handling

Real applications rarely look like a simple ?id=1 URL. SQLMap can work with POST bodies, cookies, custom headers, raw request files, proxies, delays, timeouts and retries. A saved request from Burp Suite is often the cleanest way to reproduce an authenticated lab request because it preserves headers and body structure.

01CAPTURESave the authorized request
02REPLAYConfirm it works normally
03TESTFeed request to SQLMap
04COMPAREReview detection evidence
Database Enumeration Chain
# Confirm injection sqlmap -u "http://192.168.56.10/item.php?id=1" --batch # Identify databases sqlmap -u "http://192.168.56.10/item.php?id=1" --dbs # Select one database sqlmap -u "http://192.168.56.10/item.php?id=1" -D appdb --tables # Inspect a table sqlmap -u "http://192.168.56.10/item.php?id=1" -D appdb -T users --columns # Retrieve intentionally vulnerable lab data sqlmap -u "http://192.168.56.10/item.php?id=1" -D appdb -T users --dump

This chain demonstrates the relationship between discovery and enumeration. In a real assessment, minimize data access to what the engagement requires.

SQLMap + Burp + Nmap Workflow

A practical web-security lab workflow is to use Nmap for service discovery, Burp Suite for understanding the HTTP request, and SQLMap for focused SQL injection testing. Each tool answers a different question.

01NMAPFind web services
02BROWSERMap application behavior
03BURPCapture a request
04SQLMAPTest injection
05REPORTDocument evidence
What SQLMap Does NOT Prove Automatically

BUSINESS IMPACT

SQL injection does not automatically mean every business record is exposed.

ROOT ACCESS

Database access does not automatically mean operating-system compromise.

FIX STATUS

A scan result alone does not prove a vulnerability remains after remediation.

FALSE POSITIVES

Dynamic applications require manual validation and careful response comparison.

Responsible Use

SQLMap can generate many HTTP requests and can retrieve database information. Use it only against applications you own, explicitly administer, or have permission to test. Keep enumeration and data retrieval limited to the authorized scope.

AUTHORIZED LAB ONLY: Use these examples on your own Kali/VMware/VulnHub/CTF machines or systems covered by explicit authorization. Do not run SQLMap against random public websites.
