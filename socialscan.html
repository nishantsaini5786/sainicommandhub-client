Socialscan is a Python CLI/library for checking username and email usage across supported online platforms. This reference focuses on authorized OSINT, account-name research, availability checking and structured reporting.

What is Socialscan? (Deep Theory)

Socialscan queries supported platforms to determine whether a supplied username or email is available, already used, or invalid. The original project emphasizes querying registration-related endpoints rather than simply guessing from profile-page HTTP responses.

🔎
Username OSINT: check a candidate handle across multiple services and compare where the name is available or already in use.
📧
Email support: some supported services can be queried with email addresses as well as usernames. Platform support differs by query type.

Result mental model

QUERY → PLATFORM CHECK → SUCCESS / VALID / AVAILABLE → MESSAGE / LINK → REPORT

Important: an available=False result does not automatically prove that a real person controls an account, and a failed request does not prove that an account does not exist. Rate limiting, bot protection, deleted/reserved names and platform changes can affect results.

Installation & First Run

Socialscan is distributed as a Python package. On Kali, use a suitable Python environment and verify the CLI after installation.

python3 -m pip install -U socialscan socialscan --version socialscan --help

For learning, begin with a non-sensitive test username. Then narrow the platform set and save a structured report.

Supported-Platform Thinking

Platform support is not static. The upstream Socialscan project documents username/email support for a set of platforms, but registration endpoints and anti-bot controls can change. A modern fork may have different support from the archived original.

ConceptMeaning
SuccessThe platform answered the query successfully.
ValidThe supplied value is valid for that platform's rules.
AvailableThe service reports that the username/email can be registered or is not currently in use.
UnavailableThe service reports that the value is taken or reserved.
Failed requestDo not interpret this as available/unavailable; investigate rate limits or platform changes.
Professional OSINT Workflow
1. Define scope
Decide which public test identity, brand handle or authorized research target you are investigating.
2. Normalize input
Remove duplicates and keep one username/email per line for bulk work.
3. Narrow platforms
Use -p when you only need a known set of services, reducing unnecessary requests.
4. Validate results
Separate confirmed responses from failed/rate-limited checks. Never equate a tool result with identity attribution.
5. Export evidence
Use --json so results can be preserved and processed without copying terminal output manually.
6. Report carefully
Record the query, platform, timestamp, result status and limitations. Avoid collecting unnecessary personal information.
Troubleshooting
  • Command not found: verify the package installation and Python user-bin PATH.
  • Platform returns failures: the endpoint may be rate-limiting or blocking automated requests.
  • Result looks wrong: check success/valid semantics before trusting available.
  • Some platforms work and others fail: platform APIs, registration flows and anti-bot protections change independently.
  • Bulk checks are blocked: reduce request volume, use only authorized queries and respect platform terms.
  • JSON is hard to read: use python3 -m json.tool results.json.
